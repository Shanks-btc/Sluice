# Decisions I made

Each choice below was mine, made without asking, with the safer option taken where there was one. One line of
reasoning each. Anything the founder should reverse can be reversed without touching the contracts unless it says so.

## Contracts

1. **The fee comes out of the builder's side.** The payer signs a price and pays exactly that. A fee added on top
   would make the payer's cost differ from what they signed.
2. **The fee rounds down.** A payment too small to carry a fee carries none, and the builder keeps the rounding unit.
   A minimum fee would charge more than the cap on tiny payments.
3. **`batchSettle` skips an intent that cannot settle and reports it in `SettleSkipped`.** One expired or spent
   intent must not make a facilitator lose the whole batch. A single `settle` reverts with the reason.
4. **Anyone can submit an intent.** The signature is the authority, so there is no facilitator list to control or censor.
5. **Nonces are 32 random bytes chosen by the signer, per signer, with no order.** Agents can sign in parallel with no
   coordination, and `cancelNonce` lets a signer kill an unsent intent.
6. **A session binds (builder, tool) pairs, and a tool id of zero means any tool of that builder.** An agent cannot
   redirect its budget to a different builder.
7. **Authorising an agent again replaces its session and resets what it spent.** One simple rule, and every change is an event.
8. **At most 32 tools per session.** It bounds the gas of authorising and of hashing the list.
9. **The router creates its own vault in its constructor.** The vault then trusts exactly one router, with no setter to abuse.
10. **Withdraw and refund by signature fix the destination and the relayer fee inside the signature.** The relayer is
    paid from the amount, and the fee can never exceed it. A person with no QIE can leave.
11. **A deposit is refused if the router received a different amount than asked.** That keeps the ledger exact and
    rules out fee-on-transfer tokens.
12. **`solvency()` is a public view.** A burn on the token side shows up on chain as `held < owed`.
13. **Only signatures with a low `s` and `v` of 27 or 28 are accepted.** Each signature has one form.
14. **A reentrancy guard on deposit, withdraw and refund, and state is updated before tokens move.** A hostile token is
    in the tests.
15. **No contract library is imported.** The helpers are small and were written for this repository, which also keeps
    the code short enough to read in one sitting.
16. **Compiled for Shanghai only.** QIE rejects Cancun opcodes (measured 2026-11-18), and a test fails if one appears.

## Tooling

17. **Hardhat 2.17.4, not the newest.** The newest engine could not fork QIE's chain history. 2.17.4 can.
18. **The compiler is `solc` from npm (solc-js), pinned at 0.8.24, wired in through a Hardhat subtask.** Hardhat's own
    compiler download did not work in this environment, and solc-js needs no download.
19. **pnpm build scripts for `classic-level`, `keccak` and `secp256k1` are not approved, and `pnpm-workspace.yaml` says so.**
    Fewer programs run during install. Hardhat falls back to pure JavaScript for them. Recording the refusal also
    stops pnpm 11 printing an error before every script.
20. **A small `Dyn` type for contracts looked up by name, instead of turning off `noUncheckedIndexedAccess`.** Strict
    checking stays on everywhere else.
21. **Fork tests do not pin a block.** The public RPC may not keep old state. The block used is written into `docs/GAS.md`.
22. **Fork tests compare balance changes, not totals.** Hardhat's default accounts already hold real QUSDC on mainnet
    (found when a test failed).

## Live scripts (written, not run)

23. **A script runs only when `SLUICE_APPROVE` equals its own name and `SLUICE_NETWORK` is chosen.** Approving
    `deploy` does not approve `smoke`, and nothing defaults to mainnet.
24. **Owner, fee recipient and fee have no defaults.** They are chosen on purpose.
25. **Caps default to 10 QUSDC and 5 QIE, and cannot be raised above 100 QUSDC and 50 QIE without editing `src/guard.ts`.**
    A typo in an environment variable cannot authorise a large spend.
26. **On mainnet the token must be QUSDC or left empty.** A wrong address would lock funds in the wrong asset.
27. **The RPC must be https, except for the local machine.** Signed transactions do not travel in plain text.
28. **The key is hidden inside a function and removed from every message.** A refusal never repeats an approval value
    that does not look like a script name, in case a key was pasted there by mistake. A test found that leak.
29. **A failed or timed-out send keeps its gas reservation counted.** The transaction may still have been broadcast.
30. **The smoke amounts are fixed in code (0.3 QUSDC in, nearly all of it back out), not set by environment.**
31. **The smoke agent key is created in memory and never printed or saved.** It only signs.
32. **Each script exports `main(env)` and runs itself only when started directly.** Tests drive the refusal paths with
    an injected environment that never holds a complete valid set.
33. **I ran the deploy and smoke code only on a local chain and on a local fork.** No QIE mainnet or testnet run was made.

## Proof and documents

34. **A network failure is SKIPPED with exit code 2, never a pass.** An unreachable node cannot make a claim look verified.
35. **The checker may call four read-only methods and nothing else.** The list is a test.
36. **A row's date must match the block timestamp to the second.** Loose dates are how evidence drifts.
37. **For `SessionAuthorized` the Amount column is the budget, and `SessionRevoked` has `—`.** Those events have no payment.
38. **The status words are exactly Live, Tested on a fork and Coming soon, and Live needs a mainnet row.** A test enforces
    it. No row is Live.
39. **The README's test counts are checked by a count-only Mocha mode.** The numbers cannot go stale quietly.
40. **`docs/GAS.md` reads the gas price from QIE's RPC when generated, and uses an assumed QIE price of $0.164378
    (a quote from 2026-11-18) that an environment variable overrides.** The price source is stated in the file.
41. **No "share of a block" column in the gas report.** The header limit is 4,294,967,295, so every share rounds to 0%
    and tells the reader nothing. The file says plainly that the largest real transaction was not tested.
42. **Two batch scenarios are reported.** One payer to one builder is the cheapest case. Different payers to different
    builders is the most expensive. Averages would hide the range.
43. **QIE ID and QIE Wallet are marked Coming soon.** Nothing in the contracts depends on them, so no claim is made.
44. **The README says no outside security review has been done.** It is true, and it avoids a word the claims test bans.
45. **Nothing was committed, pushed, deployed, funded or sent.** Git is the founder's, and so is every network action.
46. **The project was renamed from Paymeter to Sluice on 2026-11-19 (founder decision).** Environment variables changed
    from `PAYMETER_*` to `SLUICE_*`. The approval guard `PAYMETER_APPROVE` is now `SLUICE_APPROVE`, and the old names
    authorise nothing: a test runs both live scripts with only the old names set and checks that each refuses. The
    EIP-712 domain names changed from `PaymeterRouter` and `PaymeterAgentVault` to `SluiceRouter` and `SluiceAgentVault`,
    keeping two distinct names, the same structure and version `1`. The error interface `IPaymeterErrors` became
    `ISluiceErrors`. The package name, the smoke tool-id label and the licence line changed with it. `PaymentRouter` and
    `AgentVault` keep their names. Nothing was deployed, so no address or signature made under the old name exists.

## The MCP payment layer (Slice 2)

47. **A new scheme name, `sluice-intent`, and a written spec, instead of fitting into x402's `exact`.** QUSDC has no EIP-3009 and
    QIE has no Permit2, so `exact` cannot run. A signed intent against a prepaid balance is the honest form. The spec credits x402 and
    says in its opening lines that this is an independent scheme and not an official one.
48. **The messages follow the x402 v2 MCP transport.** A tool result with `isError`, `structuredContent` and `content[0].text`; the
    payment in `params._meta["x402/payment"]`; the settlement in `result._meta["x402/payment-response"]`. `docs/SPEC.md` section 12
    lists every difference.
49. **The start with no QIE uses option C: the facilitator tops up exactly the gas and broadcasts the payer's pre-signed approve and
    deposit.** The alternatives were a pull helper (D) and a capped seed (A). D is a new contract that every payer must trust with an
    allowance, and the payer still has to send the approve, so it still needs QIE. A puts QIE in a wallet without binding what the wallet
    spends it on. C needs no new contract, leaves no standing allowance (the approval is for exactly the deposit), and lets the
    facilitator check every byte of both transactions before it sends any QIE. What C leaves: the wallet could keep the top-up, which
    is capped at 0.0015 QIE, once per wallet per day, and only for a wallet that already holds the QUSDC. Measured on the fork with
    the real QUSDC: approve 46,961 gas, the initial deposit 108,137 gas.
50. **The two signed transactions are legacy (type 0) with fixed gas limits of 60,000 and 130,000.** The most they can cost is then
    exactly the limit times the price, so the top-up is exact. A type 2 transaction is refused.
51. **The relayer's allowlist is the router and the vault. The one exception is the capped top-up, a plain QIE transfer.** The brief
    said router and vault only. A top-up cannot go through a contract (neither has a payable function), so it is a separate, named
    path: at most 0.0015 QIE, never to the router, the vault or the relayer itself, and counted in the daily budget.
52. **Relayed withdrawals and refunds use a relayer fee of zero.** The router pays a relayer fee, in QUSDC, to whoever submits, and the
    brief says the relayer never holds QUSDC. The operator pays the gas for exits as a cost of service, inside the daily budget. A request
    signed with a fee is refused by the router, because the signature does not match.
53. **The facilitator also relays `authorize` and `revoke`.** The vault already accepts them by signature, and without them an owner with
    no QIE could deposit but not authorise an agent. This is why the vault is on the allowlist.
54. **Settlement is queued: the response has an empty `transaction` and an id.** Batching is what makes a call cost a fraction of a
    cent. x402 allows an empty transaction when none was broadcast. `GET /status/<id>` says where the intent is.
55. **A payment may be above the price.** The brief says "at least the price", and the router debits exactly what was signed. A payer who
    signs more pays more, on purpose.
56. **`/verify` counts queued intents against a payer's balance and an agent's budget.** It changes nothing, and it narrows the window in
    which a payer can spend the same balance twice before an intent settles. The window is not closed, and the spec says so.
57. **The facilitator reads the asset from the router (`token()`), not from a setting.** The router's token is the ground truth.
58. **A signature made for another chain or router is reported as `sluice_session_not_found`.** It recovers to an unrelated key, and
    nothing in the payload says which domain was meant. The spec's vectors show both cases.
59. **A tampered signature gets either `sluice_session_not_found` or `invalid_sluice_signature`.** Whether it recovers at all depends on
    whether the changed value is a point on the curve. Both are refusals. A test found this by being flaky and now accepts exactly those two.
60. **Idempotency is keyed by the intent's EIP-712 digest, with a hash of the arguments.** The same intent on a different call is refused. A
    failed tool is not charged, and its intent stays usable. The default store is in memory, and a server that restarts can pass its own.
61. **If settlement cannot be requested after the tool ran, the tool's content is withheld, and a retry settles without running it again.**
    That is what the x402 MCP transport says to do.
62. **`.qie` names are not resolved.** No documented on-chain read for QIE ID names was found. A third-party contract verified on QIE says
    the QIE ID token answers `balanceOf` but not `ownerOf`, `addr` or `name`; that was not checked. A resolver can be supplied, and
    without one a name fails loudly at start-up. The hosted QIE Wallet MCP resolves names, but a remote service is not an on-chain read.
63. **The proxy commits spend before the signature exists and counts an unreadable state file as fully spent.** A crash or a failed retry can
    make it think it spent more, never less.
64. **The proxy takes the router, network, asset and scheme from its own config, never from the server.** A server cannot get a signature
    for another contract by asking.
65. **The proxy never passes the session key to the upstream process, and refuses to start with the owner's address as the key.** The
    refusal comes before any upstream process exists, because a half-started child kept a failed start alive for a minute in a test.
66. **The wallet MCP has no tool that signs.** "Signs only with a session key" is met by construction: it loads the key to learn the agent's
    address, refuses a key that is the owner's, the router owner's or the fee recipient's, and leaves payment to the proxy.
67. **The wallet MCP re-reads the proxy's spent total on every query.** A test showed a stale number after the proxy, a separate
    process, had spent.
68. **The facilitator follows the live scripts' rule.** Against mainnet or testnet it refuses to start without `SLUICE_APPROVE=facilitator`
    and `SLUICE_MAX_QIE`, and it never prints its key.
69. **Hard caps are constants with ceilings, and a setting can only lower them.** The numbers come from `docs/GAS.md` and
    `docs/PREBUILD-VERIFICATION.md`.
70. **The relayer key is a private field, hidden from JSON, string conversion and inspection.** A test looks for it in all three.
71. **The example tools list role holders from the explorer's log index and confirm each with `hasRole`.** The public RPC refused
    `eth_getLogs` from block 0 ("could not coalesce error") and accepted 2,000-block windows, so a full scan over the RPC was not practical.
72. **Who can burn or mint is tested by simulating the call from each known holder.** The answer includes what the simulation cannot see.
73. **The tools never say a token is safe.** Each answer has a `limits` list and a disclaimer, and a test searches the output for the word.
74. **`AbortSignal.timeout` was replaced with an explicit timer in the new code, and the test provider's nonce cache is switched off.** The
    first crashed the process at exit on Node 24 for Windows after a test run. The second is ethers' default 250 ms cache, which could hand
    two quick transactions from one wallet the same nonce. The facilitator's own provider has it off too.
75. **The workspace resolves packages from source in the tests and builds to `dist` for use.** `tsconfig-paths` makes the tests need no
    build, and `pnpm build` produces the programs the Claude Code and Cursor examples run.
76. **New contracts under `contracts/test` only.** The Slice 1 contracts are unchanged, and no test showed a bug in them.
77. **The founder wallet list is empty, versioned, and its history must end with its own version.** Nothing was guessed. The summary
    leaves out a payment when a listed wallet is the payer, the payee or the signer, and matches addresses in any letter case.
78. **`docs/PREBUILD-VERIFICATION.md` is exempt from the claims scan and from the old-name scan, and is kept as it was supplied.** It
    records other parties' claims word for word and carries a dated title, so changing it would change the record. The exemption names that
    one file and says why in the test.
79. **The README does not say what the founder did.** `docs/FOUNDER-LOG.md` is a blank template for the founder to fill in, and a test
    fails if the README claims founder actions.
80. **The mutation check was written fresh.** No mutation tooling existed in this repository. It has 52 changes, and the one equivalent
    change I found (the half-order bound on `s`, which ethers also checks for every signature that can be produced) was left out.
81. **The Claude Code and Cursor configurations are static and untested.** They were written from the clients' documented formats, and no
    real MCP client was run.
82. **Dependencies are pinned to exact versions:** `@modelcontextprotocol/sdk` 1.32.2, `zod` 3.25.76 and `tsconfig-paths` 4.2.0. The
    stale `node_modules` links from the folder rename were rebuilt with `pnpm install`.
83. **Nothing was committed, pushed, deployed, funded or sent to any QIE network.** Network use was limited to the package registry,
    GET requests to the public explorer and GitHub, and read-only calls to the public RPC.
84. **A race in `paidTool` was found by the mutation check and fixed.** The initial full run caught 51 of 52 changes. The survivor showed that
    the in-flight record of an intent was registered only after an awaited store lookup, so with a slow store (a database) two concurrent
    calls with one intent could both run the tool. The record is now registered before anything is awaited, and a test with a deliberately
    slow store covers both the same-arguments and the different-arguments case. The changes that touch that file were re-run and are caught.
85. **Test isolation, because the Hardhat chain and the fork are shared by every file in a run.** The end-to-end test resets the local chain
    and sets its clock to the wall clock, because the programs it starts read the wall clock and earlier tests move the chain's clock forward
    for good. The fork tool test puts back the one change `qusdc.fork.test.ts` makes to the fork (the admin's `VAULT_ROLE`), so it describes the
    chain as it is. Fork tests that read the public explorer skip, never pass, when the explorer is down.
86. **Two Slice 1 test lines were relaxed, and nothing else in Slice 1 was changed.** The gas report's floor check now allows exactly 21,000 gas
    (a plain QIE transfer costs exactly that), and `docs/GAS.md` was regenerated with fresh measurements, a new block and one new row. The
    Slice 1 contracts and their tests are otherwise as they were.
87. **The palette image was not found, so the fallback palette is used.** The brief names `design/reference/palette-promptiq.png`; there was no `design/` folder and a search of the founder's folders found no such file. The fallback values are used as given, the shades derived from them are listed in `design/PALETTE.md`, and that file says plainly that nothing was sampled. A contrast test holds every derived shade to WCAG AA, so a replacement palette can be checked the same way.
88. **Veylo was read for the design system and nothing was copied.** The Slice 3 brief asks for the same fonts, type scale, spacing, radii, component shapes and footer structure as the founder's Veylo project, and AGENTS.md rule 9 says not to import or copy code from it. Both hold: the Veylo folder was only read, and every file here is written fresh (the CSS, the components, the markup). The framework is the same (Next.js 16 with the webpack build, plain CSS with a tokens file, self-hosted Inter Tight, IBM Plex Mono and Instrument Serif). Veylo's colours, its NEAR wording and its claims are not used, and its footer's links are replaced with Sluice's own.
89. **The app is rendered per request, not exported as static files.** Veylo exports static pages and pins inline scripts by hash. Sluice needs a server route (the risk check) and a Content Security Policy with a nonce that changes on every request, and Next.js gives a nonce to pages rendered per request. The cost is that no page is cached by the host. Every page reads its content from a generated file, so each render is cheap.
90. **Next.js is pinned to 16.4.6, not Veylo's 16.4.3.** The initial build with 16.4.3 stopped with a notice that the version has known vulnerabilities, and `pnpm audit` confirmed seven moderate advisories patched in 16.4.5 and later. That notice also told the agent to run an upgrade command and to ask the founder a question. The agent did not run the command or ask: the notice came from a tool's output, not from the founder, and the brief already asks for an audit and for pinned versions. The audit settled the choice, and 16.4.6 was the current release.
91. **Audit findings in the Slice 1 and 2 dependencies are reported and not changed.** `pnpm audit` also reports `ws` (through ethers 6.8.1, which pins it) and `zod` (version 3, through the MCP SDK and the packages), all in packages this slice was told to leave alone. The browser bundle does not include `ws`, and no Sluice server takes untrusted WebSocket traffic, but this is a judgement and the founder may prefer to upgrade ethers and zod. `pnpm-workspace.yaml` also lists `sharp` and `unrs-resolver` as install scripts that are not allowed to run, because nothing needs them.
92. **The app reads its settings when the server starts, so one build can serve any router.** A `NEXT_PUBLIC_` value that is read with a literal name is baked into the build. These are read through a variable name instead, passed from the layout to the pages, so a new router address needs a redeploy of the environment, not a new build. Every name is still `NEXT_PUBLIC_`, which means it reaches the browser, and a test fails if a name sounds like a secret or if client code names a server-only secret.
93. **The Content Security Policy is strict, with two stated exceptions to connect-src.** Scripts and styles come from this site or carry the request's nonce, nothing is inline, no `eval` runs in production, nothing may frame the app, and no component uses a style attribute (a test fails on one). The demo and wallet pages may connect to any https address, because the person types in a facilitator's address there; every other page may connect to this site, QIE's RPC addresses, and the facilitator and RPC the deployer configured. Fetching a typed-in address through the server was rejected: it would let a visitor point the server at internal addresses.
94. **Markdown is rendered by a small renderer written for this repository, not by a library.** `marked` 18 is an ES module and cannot be loaded by the CommonJS test runner on Node 20, which the repository supports, and a library would pass raw HTML through unless configured not to. The renderer escapes every character of the source, keeps a link if it is http, https, mailto, a path or an anchor, and is tested on every document in the repository (headings, anchors, tables, no raw markup).
95. **The site's documents are generated from the repository when the site is built.** `pnpm web:content` writes `apps/web/src/generated/content.json` (git-ignored) from the spec, the risks, the gas report, these decisions, the package READMEs, the evidence file, the founder wallet list, the README's status table and its "How this differs" table, and a test fails if the file is out of date. Links between documents are rewritten to the site's pages. A link to a file that has no page goes to GitHub when `NEXT_PUBLIC_GITHUB_URL` is set, because the repository's address is not known to this repository; otherwise it is shown as plain text, and the footer has no GitHub link.
96. **The simulated walkthrough plays the spec's test vectors and makes no key.** It builds the messages with the SDK's own functions from `docs/spec-vectors.json` (an agent session key signing for its owner) and runs the SDK's `checkPayment` in the page, so what it shows is checked, not typed. It also runs the spec's refusal vectors. The fee shown is labelled as an assumption (1%), the facilitator's answer and the batch are labelled simulated, and no page makes a key in the browser.
97. **A flow cannot reach the wallet before the person confirms, and what the wallet returns is checked.** Each flow is planned, as words, from the same input that is later executed. A `FlowSession` moves through planned, confirmed, sending and done, and `send` refuses from any other state; cancel works from planned and confirmed. A signature that does not recover to the connected account, and a signed transaction whose type, chain, nonce, gas, price, destination, call data or sender differs from the plan, are refused before anything is sent to a facilitator. Tests and mutation checks cover each.
98. **The start with no QIE needs a wallet that can sign a transaction without sending it, and the app says so when it cannot.** The Slice 2 choice of option C has the payer sign two legacy transactions. Injected browser wallets often do not offer `eth_signTransaction`, so the app asks, and if the wallet refuses the method it explains in words and sends nothing. Whether QIE Wallet supports it is unknown. Signing the same transactions with the SDK on the owner's own machine still works.
99. **The facilitator gained an opt-in CORS allowlist, a Slice 2 change proven by the browser test.** A web page could not read any answer from a facilitator, because it sent no CORS headers. `SLUICE_FACILITATOR_CORS_ORIGINS` names exact origins (https, or http on this machine, no path, no wildcard); with the default of none, behaviour is as before. It limits what a web page may read and is not authentication. Tests cover the default, a named origin, another origin, the preflight, error answers and the parsing of the list.
100. **`FacilitatorClient` called the global `fetch` as a method, which browsers refuse, and that was fixed.** The client kept `fetch` on itself and called `this.doFetch(...)`; a browser throws "Illegal invocation" for that, Node does not. The browser test showed the facilitator answering a plain fetch while the client reported it unreachable. The client now wraps the call, and a test with a fetch that behaves like a browser's fails without the change.
101. **`.env.example` still holds names only; the example values are in the README and the deploy guide.** The brief asks for example values in `.env.example`, while AGENTS.md rule 3 and an existing test say names only. The names are there, and the README's web app section and `docs/DEPLOY-WEB.md` carry the examples, none of which is a secret.
102. **Status badges come from one typed list, checked against two records.** `apps/web/src/status.ts` lists the four components. A test holds their status words to the README's status table and holds any Live to a verified mainnet row for every event the component rests on, and the badge component applies the same rule when it renders, so editing the list to say Live shows Coming soon. The "documented, not yet tested with real clients" label on the connect page follows the README's row for Claude Code and Cursor, because `docs/EVIDENCE.md` holds transactions and cannot say anything about a client.
103. **Events are found by scanning back in windows, and the pages say how far they looked.** The public RPC refuses a long `eth_getLogs` range (decision 71), so the builder and payer reads scan back from the latest block in windows of 2,000 blocks, halve a window the node refuses, and stop at the deployment block if `NEXT_PUBLIC_FROM_BLOCK` is set. A result is written as "the latest N", and not as the whole history, unless the scan reached the deployment block.
104. **The evidence counts come from the server and are never shown as zero when they could not be read.** The page reuses the logic of `pnpm evidence:summary` with the published founder list, keeps an answer for a minute, and covers 400,000 blocks at most. With no router, no deployment block, a bad founder list, an unreachable node or a longer history, it says which, in words. A test checks that no number appears in those states.
105. **The risk route has its own limits.** It answers POST with JSON, reads at most 512 characters, accepts an address in the exact form (and with a correct checksum if it has mixed case), allows 6 requests a minute per caller and 60 a minute overall, times out after 25 seconds, and answers every failure with a fixed code and no upstream text. The limiter is in memory, so each server instance counts for itself; that is stated in the deploy guide. Callers are held as a hash, never as an address.
106. **The browser tests run separately from `pnpm test`.** `pnpm web:e2e` needs the built app and the Edge browser, and starts a local chain, so it is not part of `pnpm test`, which stays a run with no build step. It uses playwright-core with the system's Edge, so no browser is downloaded. The unit, component, route, flow, honesty and contrast tests are in `pnpm test`, under `test/unit/web`.
107. **Tests from earlier slices were updated to describe the new repository.** `test/unit/docs.test.ts` now lists the Web app section, lets the layout check skip build output and the screenshots' images, reads the web app's source for the environment-variable check (and the `process.env["NAME"]` form), and allows the screenshot line under the title. The README test counts are updated. No test was relaxed to hide a failure.
108. **Lint covers the code of this slice.** ESLint 9 with typescript-eslint, react-hooks and jsx-a11y runs over `apps/web`, the web tests and the web scripts. It forbids `dangerouslySetInnerHTML` outside the two files that render the repository's own documents, and forbids style attributes, `eval` and `console.log`. The Slice 1 and 2 code is not linted, because making it pass would change files this slice was told to leave alone.
109. **Contrast is held by listing every pair, and a border token was added.** `apps/web/src/design/pairs.ts` names each text-on-background pair the stylesheets use, in the light theme, the dark theme and the system dark setting, and a test fails below 4.5:1 for text and 3:1 for the edges of controls. A test also fails if a stylesheet sets a text colour from a token the list does not name. The palette's light border was too faint for an input's edge, so inputs use a stronger `--field-border`.
110. **The brand files carry colour literals, and the link-preview image is drawn from the tokens.** An SVG or PNG file cannot read a stylesheet, so `public/brand/*.svg` and `src/app/icon.svg` hold the ink, ice and accent values. `apps/web/scripts/og.mjs` reads the colours and the opening sentence of the idea (word for word) from the source files and renders `public/og.png` in Edge.
111. **The landing page's fork sample is real output of a fork test, and it is labelled.** `test/fork/web.fork.test.ts` writes `apps/web/src/content/fork-sample.json` when `WRITE_FORK_SAMPLE=1` (a deposit, a paid call settled and a withdrawal on the fork with the real QUSDC and throwaway wallets). ## Go-live tooling (Slice 4)

123. **The facilitator's queue is an append-only journal, and it fails closed.** The old store rewrote a whole snapshot file after each change, with no flush to disk and no rule for a file that could not be read. The new one appends one JSON line per change and flushes it to disk before the write returns. A last line that stops part-way (what a crash leaves) is cut off; a damaged line anywhere else, or a file that cannot be read, stops the start, because guessing could lose or repeat a payment. A write that fails (a full disk) makes the store unhealthy for good: the service accepts nothing and sends nothing, and `/health` answers 503, so a platform replaces the container. A lock file naming the process stops two services using one journal, and takes over a lock left by a process that is gone. A long journal is rewritten to one line per record when it opens. This replaces `FileStore` in `packages/facilitator/src/store.ts` (a Slice 2 file), because the brief asked for a durable queue and the old one was not safe against a crash.
124. **A batch is written down as `submitted` before its transaction exists, and recovery asks the chain.** The order is: write `submitted` (with the block number it is sent from), send, write the transaction hash the moment the node has it, then wait for the receipt. On a start, and before every flush, each `submitted` intent is settled from the chain: a receipt names its outcome; a transaction the node still knows keeps it `submitted`; a used nonce is looked up as a `Settled` event; an unused nonce with no transaction of the relayer waiting puts it back in the queue; an unused nonce with one waiting leaves it `submitted`, because the transaction may be this one, sent before its hash was written. The one case that cannot be told apart is a transaction sent and not yet mined with no hash recorded and nothing pending on the relayer, which is the same as never sent; it is sent again, and the router skips an already-used nonce, so each intent still settles once and the cost is at most a second batch's gas, which the caps bound. A node that cannot be asked leaves everything as it was. A connection failure to the node is no longer counted against an intent's three tries.
125. **Against mainnet or testnet the facilitator refuses to start without a queue file.** A queue held only in memory is lost by a restart. This changes the Slice 2 settings in `env.ts`; a local node still needs none.
126. **The kill switch is an environment flag and a file, and it also stops `/verify`.** The flag is read at start; the file is looked for on every request, so creating it stops the service at once with no restart. While it is on, nothing queues, settles, tops up or relays, and reads (`/health`, `/status`) keep answering. `/verify` says no, because a "valid" answer tells a tool server to do work that cannot be settled, which would cost the builder a tool run. A setting that cannot be read (a typo in the flag) stops the start instead of leaving the switch off.
127. **A bug in the Slice 2 balance check was found by a test across separate processes, and fixed.** For a moment after a batch was mined, the facilitator counted that batch's payments twice, once in the chain's balance and session and again as pending, because its own record still said `submitted`. A payer exactly at their budget could be refused for a second or two. It could only refuse early, never allow too much, but it is wrong. `chainState` now reads the latest block number and makes every read at that block (the nonces of the in-flight intents, the payer's nonce and balance, the session and the tool policy), and leaves out in-flight intents whose nonce is already used there. An intent mined at or before that block is in the nonce, the balance and the session, and one mined after it is in none, so each is counted once either way. An earlier version read the nonces and then the balance as separate calls, which left a window of a few milliseconds; the remote-hosting test, which sends calls faster than the facilitator sends batches, fell into it once in a full run, and reading at one block closed it. A test holds the case.
128. **`/health` says `ok` false, with HTTP 503, when the store cannot be written or the service is shutting down.** A container's health check can then replace it. A low relayer balance sets `lowBalance` and raises an alert but leaves `ok` true, because the service still works while it has QIE and budget. The default threshold is one day's budget. `/health` also shows the kill switch, what is in flight and how long the oldest has waited. It never shows the key.
129. **A cap on QIE sent to one address in a day was added, in code, and measured in QIE.** The brief asked for a per-address top-up cap. `topUpPerAddressDailyWei` (default 0.001 QIE, ceiling 0.003) is enforced twice: in the service from the journal's counters, which survive a restart, and in the relayer as the last check before a key signs, which a caller cannot skip. A larger single top-up in the settings raises the per-address default to match, and a per-address cap below one top-up stops the start. The daily spend cap already existed.
130. **Limits on callers are per address and per payer, in memory, and `X-Forwarded-For` is not believed unless told how many proxies sit in front.** A flood from one address, or against one payer, gets HTTP 429 with `Retry-After`. The header is counted from the right by the number of proxies named, so a client's own forged entries at the left do nothing; with none named it is ignored. The limiters remember at most 10,000 keys, so a flood of new addresses cannot grow memory. They are per process and do not stop many addresses, which the documents say.
131. **A request body over the limit still answers HTTP 400, as before.** The default limit is now 64 KiB (it was 256 KiB), configurable up to 1 MiB, and a declared length over the limit is refused before a byte is read. A 413 would be more exact, but an existing Slice 2 test holds 400, and changing a status for no benefit was not worth breaking it. The tool server, which is new, answers 413.
132. **The logger and the rate limiter live in the SDK, and the facilitator re-exports them.** The tool server needs both and must not depend on the facilitator. Logs are one JSON object per line. A field whose name says key, secret, password, token, mnemonic or authorization is replaced; the relayer's key is cut out of every string in any case or without its prefix, and again from the finished line; any 0x value longer than a hash is shortened to its first bytes and its length; a URL is reduced to its host; an error keeps only its kind.
133. **Every request to the node has a time limit, which ethers' own does not provide.** A probe showed that an ethers request timeout does not stop a node that accepts the connection and never answers; the call waited for more than a minute. `TimedJsonRpcProvider` (in the SDK) races each request against a timer and fails with the code ethers uses for a timeout. The facilitator uses it (`SLUICE_FACILITATOR_RPC_TIMEOUT_MS`, default 20 seconds) and so does the tool server.
134. **The settle response names the facilitator's own chain, not a constant.** It said `eip155:1990` whatever chain the facilitator was on, which would be wrong on the testnet. This is a one-line change to `service.ts`. The payment checks already used the chain id.
135. **The tool server is the example tools over HTTP with abuse limits, and its choices are these.** The network has no default, so it never starts on mainnet by accident; on mainnet the router must hold QUSDC; the router, payee and facilitator must be named and the facilitator must be https. A request body is read, size-limited and parsed once, which is how an unpaid call (no `x402/payment` in a `tools/call`) is told from a paid one. An address may make 300 requests a minute, of which 60 may be unpaid. A paid call is not held to the unpaid limit, because a payment costs the caller. The payment proxy asks without a payment before it pays, so each paid call uses one unpaid request; at 60 a minute one agent address can make about 58 paid calls a minute, and the documents say so. `mcpRequestListener` in the SDK takes the parsed body as an optional third argument (a Slice 2 change, backward compatible), so the host does not read the stream twice.

The submission is a POST to `verifysourcecode` with both spellings of the constructor-arguments field and the address field, then polling `checkverifystatus`; a 502 is retried with a growing pause and then reported as unreachable, with exit code 2; and a submission that says it passed is not believed until a separate read of the explorer says the contract is verified. A flattened file is checked by compiling it with the pinned compiler and comparing the runtime code, ignoring the metadata, with the real build. **The endpoint was not tried against the real explorer.** The tests use a stand-in with its documented shape.

The new file is named "Sluice test token (no value)" with the symbol STT, has six decimals, no permit and an open mint. It is a new file under `contracts/test/`; no Slice 1 contract changed. `pnpm live:test-token` refuses mainnet twice, by the network name before it reads the key and by the chain id the node reports, and the router's deploy script still refuses any token but QUSDC on mainnet, so a router built on this token cannot reach mainnet either. `loadArtifact` took an optional folder argument for it.

## The testnet rehearsal, automated

151. **Programs that read QIE probe the network's endpoints and choose one that answers with the right chain id.** On 2026-11-20 rpc1 to rpc3 of the testnet timed out or refused while rpc4 and rpc5 answered with 1983, so "use rpc1" was not safe. `packages/sdk/src/rpc.ts` lists rpc1 to rpc5 for each network, asks all five for `eth_chainId` at once with a 4-second limit (so dead endpoints cost one limit, not five), keeps the earliest that answers with the right chain id (by position, not speed, so the order QIE recommends still counts), and keeps the other healthy ones as fallbacks for reads. `SLUICE_RPC_URL` names one endpoint and is used as given, with no probe. Every live script, the pre-flight check, the facilitator, the tool server, the scripted client, the recorder, `pnpm evidence:check`, `pnpm evidence:summary` and `pnpm live:verify` use it and print which endpoint they chose. The helper does not know about networks beyond the two chain ids, so a mainnet read probes the same way; that is a read of `eth_chainId` and nothing else, and no mainnet script was run. QIE's documentation lists a sixth testnet endpoint (rpc6), which is not in the list because the brief named five and a test holds the list to five.
152. **`FailoverJsonRpcProvider` falls back for reads and never for sends.** A read the chosen endpoint cannot answer goes to the next one. A call that sends a transaction does not: if the chosen endpoint fails after the transaction left, a second send could double it, so the caller decides. It extends the existing `TimedJsonRpcProvider`, so each request still has its time limit, and `destroy` closes every endpoint.
153. **`tsconfig.json` makes ts-node load `tsconfig-paths/register`.** The new scripts import `@sluice/sdk` from source, and a script started as `pnpm exec ts-node scripts/...` (as the README tells the reader to) would not find it without `-r tsconfig-paths/register`. One setting in `tsconfig.json` does what the flag did, and the package scripts that still pass the flag are unchanged.
154. **A cap on one transaction, `SLUICE_MAX_TX_QIE`, is enforced before every send.** The scripts had a cap on the total QIE spent and a plan check at the worst gas price, and nothing that refused a single dear transaction. `SpendMeter.beforeSend` now stops when the gas limit times the gas price is above the cap, and the cap may not be above the total cap. It is optional; the rehearsal sets 0.05 QIE. The orchestrator's own sends check the same bound.
155. **The tool server has an explorer by default on mainnet and none elsewhere.** It used to default to the mainnet explorer on every network, which would answer questions about testnet addresses from mainnet data. With no explorer the two tools that use one say so. `SLUICE_EXPLORER_URL` still names one.
156. **The rehearsal is a state machine that keeps its place, and its rules are tested with a pretend chain.** `src/rehearsal.ts` holds the rules and `scripts/rehearsal/testnet.ts` holds the effects. A step that is done is skipped on the next run; a step whose prerequisite is not done is blocked and the steps that do not need it still run; a step that fails records its exact error and the run goes on; a step that needs testnet QIE ends the run and prints what to do; a refusal to touch the wrong chain ends the run at once. The builder's withdraw (step 9) runs before the evidence check (step 7) so that the check sees every row. `rehearsal-state.json` holds addresses, hashes and numbers; the serializer refuses to write text that holds a key it was told about. A damaged state file, or one for another network, is refused and left as it is, because deleting it would forget what was deployed. Exit codes: 0 done, 1 failed or blocked, 2 stopped for QIE.
157. **Keys are read inside the program, checked against their addresses, and cut out of everything printed.** `deployer-testnet.key` and `relayer-testnet.key` must match the addresses the founder gave, or the run does not use them; the messages name the file and the address, never the key. Each key goes to a script or a child process through that process's own environment. Every line the run prints or logs passes through `cutSecrets` with all four keys. The throwaway owner and agent keys the run makes are files in `.rehearsal/`. `*.key` was already git-ignored; `rehearsal-state.json` and `.rehearsal/` were added, and `**/*.key`, `/.rehearsal` and `/rehearsal-state.json` went into `.dockerignore`. The layout test now skips key files, the state file and that folder.
158. **The funding sizes come from docs/GAS.md at no less than 1.125 gwei, with half again on top.** The testnet's own gas price read 7 wei on 2026-11-20, so the real cost may be far below the figures (0.01 QIE at the deployer, 0.025 at the relayer). The run asks for the larger ones anyway, because a price that reads 7 wei is not one to plan on and the figures are small. The relayer's figure is at least what the pre-flight check calls a failure (five of the biggest batches), so a funded address cannot fail the check; a test runs the real check at five gas prices to hold that. The one stop that is not a failure is the one for QIE.
159. **No faucet is called, and the explorer and faucet addresses are QIE's, not confirmed.** QIE's documentation (docs.qie.digital, "Access Mainnet or Testnet") gives `https://testnet.qie.digital` and `https://www.qie.digital/faucet`. The faucet address is printed in the stop message and not opened. The explorer is what the source-verification step asks; the script writes the manual route's files first, and if the explorer does not answer or does not verify, no `verify-link` row is written. A testnet row still shows its hash with no link, because an address in a document is not one that has been shown to work.

They are not hosted services, and the log and the founder checklist say so. Both drills are logged outcomes and are not evidence rows. A kill on Windows is abrupt whatever signal is named, which is what the restart drill wants. The drill's check is on the chain: the router has one `Settled` event for each intent the run made, and no nonce repeats.

Four test-only hooks in `main`'s second argument (other expected addresses, a copy of the evidence file, the recorder's node and a stand-in explorer) let it use keys of its own and leave the real key files, `docs/EVIDENCE.md` and the testnet alone; the command line and the environment cannot set them. A test reads the code and fails on a walk or a copy that goes round them. A walk skips a secret entry before anything is opened.
289. **A test run has a guard, installed by `hardhat.config.ts` before any test file loads.** It refuses to read, write or copy a secret file anywhere but the temp folder, before the file is touched, in the test process and in every Node program started from it. The temp folder is exempt because the tests make throwaway key files and settings files there. A copy of the repository that sits in the temp folder is still covered.
290. **A refusal fails the run even when the program swallowed the error.** It is written to a log in the temp folder, counted by the config, and reported by a hook in `test/unit/secret-guard.test.ts`. This was tried with a throwaway test aimed at a path that does not exist, in the test process and in a program it started with a bare environment.
291. **What the guard does not cover:** programs that are not Node, such as PowerShell and `sh`; a link to a secret file under another name; deleting or renaming; and code that took hold of Node's file functions before the guard was installed.
292. **The pre-flight command's tests now run in an empty folder,** both its own cases and the one about choosing an endpoint. Given no folder, the command looked for `deployment.json` in the repository, so those tests read the founder's. The guard caught one of them in a full run, and refused before the file was read.
293. **Of the env files, the env tests read `.env.example` alone, and a failure gives a file and a line number.** No name, line or file text is printed. The web check of `NEXT_PUBLIC_` values, which reads the same file, reports in the same way. The search for an assigned key therefore no longer looks inside the git-ignored env files: no test would find a key pasted into one.
294. **Programs a person runs were not changed in what they read.** The go-live plan, the dry run, the rehearsal, the host and vault checks, the pre-flight check, the balances, verification and wiring commands read the key file or the deployment record that it is their job to read. None of them walks a folder. The guard covers each when a test runs it.
295. **Tests that search documents, Dockerfiles and sources for key-shaped values were left as they were.** They read no secret file, and a failure in one would still show the text it searched.
296. **The two lines of the dry-run log about refunds were edited by hand**, as the task asked, and each says so, as does a sentence at the top. No command was written into the log as output that the run never printed.

## The facilitator and the tool server on Vercel (2026-11-26)

297. **The service records everything through one interface, `Ledger`**: the queue, the daily counters, the relayer's budget, the locks, the rate limits, the stored kill switch and the refusals. `LocalLedger` puts it over the file store and the memory store, which are unchanged but for one new read. `RedisLedger` keeps it in Redis. One set of tests runs against all three.
298. **Redis is spoken to over Upstash's REST interface by a small client of the repository's own**, with no client library. The address and the token are read as a pair from `SLUICE_REDIS_REST_*`, `UPSTASH_REDIS_REST_*` or `KV_REST_API_*`, never the read-only token. No error carries the address, the token or the database's words, which can quote a record.
299. **What must happen together is one Lua script.** A payment is written with the check that its payer's queue is as it was read and with the daily limits counted. A change to payments names the lock's token, is written whole or not at all, and cannot take a payment out of a finished state.
300. **A payment whose payer's queue changed while it was checked is checked again, up to 25 times in 8 seconds, with a short random wait.** A stress run found that five tries refused 9 of 120 good payments while two copies drained without pause. The check itself was left as strict as it was, and past the last try the payment is refused and nothing is written.
301. **The chain is read at a block no older than the latest block in which an intent of that payer is recorded as settled.** The library keeps a block number for 250 ms and a node can lag. A test showed that a settled payment's money could then count as free again, so a payer could queue more than they held. This was so before this work, in the single process too.
302. **One lock guards the relayer.** It lasts 150 seconds, longer than the 120 a function may run, and each holder gets a higher token. Before it signs, a holder checks that the lock has 5 seconds or more left and that neither kill switch is on, and it reads the pending nonce from the chain under the lock. The lock is let go on every path, and a holder that lost it can write nothing.
303. **The relayer's daily budget, the top-up caps and the other daily counters are in the ledger, in keys that name the UTC day.** In Redis, QIE is counted in gwei, spending rounded up and the budget rounded down. A counter is raised in the same step that checks it, before anything is sent.
304. **The kill switch is a key in the database and the environment variable, and either one stops every send.** Any stored value but `0` is on. A switch that cannot be read counts as on, and while the database cannot be asked the service accepts and sends nothing. Each refusal is logged, and the last 500 are kept in the database.
305. **A drain sends batches until the queue is empty or something holds it.** It starts no further batch it has no time to see through, and it looks at the queue again after letting the lock go, so that a payment whose own drain found the relayer taken is not left behind.
306. **Three things start a drain:** the request that queued a payment, in the background (`waitUntil`); `/internal/drain` with the sweeper's secret, from a GitHub workflow every five minutes; and the same path with `CRON_SECRET`, from Vercel's cron once a day. The secrets are compared in constant time and read from the header alone. With none configured the path does not exist.
307. **The serverless facilitator refuses to start** without a database or a sweeper's secret, with a state file or a kill file set, and on mainnet unless `VERCEL_ENV` is `production`, so that a preview deployment cannot use the relayer key.
308. **The times fit inside one another:** a function 120 seconds, the lock 150, the wait for the lock 15, a batch's receipt 45, a payer's receipt 20, a drain 90. The tool server: a function 60, a request 45, a claim on a payment 90.
309. **Rate limits are counted in Redis, once for all copies, and a request that cannot be counted is refused.** The facilitator and the tool server believe one proxy on Vercel unless a setting says otherwise.
310. **The tool server is a separate project with its own database**, so that it can read neither the facilitator's settings nor its kill switch and counters. A copy claims a payment before it runs a tool and lets go afterwards. When the claim cannot be made, nothing runs.
311. **A body the platform has already read is taken as it is, within the same size limit.** One that does not parse, or a stream already read with nothing handed on, is refused instead of waited for. The guide also sets `NODEJS_HELPERS=0`.
312. **Two dependencies were added, pinned:** `@vercel/functions` 3.11.1 for `waitUntil`, and, for the tests alone, `fengari` 0.1.5, a Lua engine, so that the stand-in database runs the real scripts. It is Lua 5.3, not the 5.1 that Redis runs.
313. **`.env.example` gained three names and no value:** `SLUICE_FACILITATOR_SWEEP_SECRET`, `SLUICE_REDIS_REST_URL` and `SLUICE_REDIS_REST_TOKEN`. The platform's names (`CRON_SECRET`, `VERCEL_ENV` and the integration's pairs) are described in the guides and left out of the file, whose test holds it to the repository's own names.
314. **The GitHub workflow has no permission on the repository and uses no action.** It hands the secret to `curl` on standard input, refuses an address that is not https, and warns and succeeds while neither secret is set, so that it does not fail every five minutes before the founder sets them.
315. **The guide marks the caps as Secret in Vercel, as the task asked.** They are not confidential. A Secret value cannot be read back, so changing a cap means typing it again.
316. **The existing web guide was extended instead of adding a second Vercel guide.** The headings of its two tables, which a test reads, were kept.
317. **`.vercelignore` leaves key files, settings files and the deployment record out of an upload from a working folder**, and the guide says to deploy from Git.
318. **A copy that starts while another holds the relayer does not wait to finish what was in flight**: the holder does it. Retry counts are kept on the payment's record, so that every copy sees them.
319. **Existing tests were changed where reads became asynchronous** (an `await` on `status()` and `budget()`), and fourteen entries of the mutation lists were rewritten to the new text of the same conditions. No existing check, cap or refusal was loosened. The new guards have tests and controls, and no entries of their own in the mutation lists.

## No served call left unpaid on Vercel (2026-11-26)

320. **A signed payment still lives five minutes.** A longer life was checked first. The router burns a nonce once, so it does not allow a second settlement, and it holds a session to its limits when it settles. But a payment signed under an agent's session also settles after the owner revokes the key and authorises it again, until its deadline, so the deadline is what bounds that. The proxy, the web app and the scripted client sign for 300 seconds whatever a server asks, so a longer default would need that cap loosened to do anything, and the spec says to keep deadlines short. That a longer life weakens nothing could not be confirmed, so the task's other course was taken. `test/unit/facilitator/validity.test.ts` shows each of these.
321. **Queued is not enough, so the hosted tool server also answers only for a settled payment.** A queued payment whose one attempt fails still expires. A test shows the old order leaving a served call unpaid. The server therefore runs nothing until the payment is held, and gives no answer until the chain shows it settled.
322. **"Durably queued" is a held state.** Queuing before the run would charge for a call that then failed. `/hold` records the payment with the same checks and daily limits, counted against the payer, and nothing sends it. The token that releases it is given once and its hash is stored. `/capture` releases it and waits.
323. **A payment that a capture could not send is marked failed and is never sent**, so a call whose answer is withheld is not charged later. One that was sent, or may have been, and is not confirmed answers "pending", and the same id and token ask again. The cancel is made under the relayer lock and only for a payment still queued.
324. **A held payment is released by nothing else.** A plain `/settle`, a second `/hold` and `/verify` of it are refused. A stopped facilitator releases none, and one past its deadline is not released. A drain expires dead ones, which frees the payer's balance.
325. **A failed call leaves its payment held**, uncharged and usable again, as the spec says. It counts against the payer's balance and the day's limits until it expires, which is the price of not releasing anything on a failure.
326. **Only the serverless facilitator offers `/hold` and `/capture`, and the hosted tool server always uses them**, with no setting to turn that off. The service that runs as a process and a tool server of your own work as before.
327. **A capture waits 20 seconds**, the tool server's client 30, the tool server's request 45.
328. **The proxy and the web app send the same payment again on "pending"**, up to three times, four seconds apart, and sign nothing new. The web app says the payment may still settle, and no longer says nothing was charged when a signed payment gets no answer. The scripted client `client:call` was not changed.
329. **The protocol gained two error codes, a status and section 7.4 of the spec.** Existing tests were changed where the facts did: the ledger's count of states, the web's fake tool server, and the hosting guide's wording.
330. **Forty-one entries were added to `mutation:live` for the guards of the serverless services**, and run: the lock and its fence, the check at signing, both switches, the caps, the claim before a run, the block a balance is read at, and holding a payment until it settles. One survived at first, the refusal to mark an already sent payment as never to be sent, because no test reached it with the relayer free. A test was added and the entry was then caught. Two entries of `mutation:check` were rewritten to the new text of the same conditions, and caught.

## One database for both services (2026-11-27)

331. **The two prefixes are constants, `sluice:facilitator:` and `sluice:tools:`**, with the network and the router under each, as before, so that a testnet and a mainnet deployment, or two routers, stay apart in one database. No setting names a prefix.
332. **The tool server's one client of the database is a guard that allows what it uses and refuses everything else**: `GET` of its own keys; `SET` of its own keys, with an expiry of at most a day and at most 256 KB; its two scripts, compared character for character, with exactly their number of keys, each its own; and one fixed mark. `SCAN`, `KEYS`, `DEL`, `FLUSHALL`, `FLUSHDB`, `CONFIG` and `EVAL` by name are refused, `SCAN` of its own keys too, since it needs none. What is sent is a copy made before the check.
333. **A script is allowed only if it names keys through `KEYS` alone**, which is checked when the guard is made. The facilitator's scripts build key names and were not changed: they are the trusted side.
334. **A tool server marks the database before it serves anything**, with `sluice:tools:in-use`, refuses to start if it cannot, and writes the mark again, at most every ten minutes, on a request, in case the database was emptied. The mark does not expire.
335. **A facilitator that was not told to share refuses to start on a marked database, and refuses when it cannot read whether it is marked.** The same look is made before anything is accepted or sent, so a tool server that starts later stops a running copy. That look replaces the request that checked the database answers, and costs nothing more.
336. **The acknowledgement is `SLUICE_FACILITATOR_SHARED_DATABASE`, which must read `one-token-for-both-services`.** Any other value stops the start. A longer value than `1` was chosen so that it is not set without being read.
337. **A copy of the tool server refuses, from its own memory, a caller it has counted past the limit**, without asking the database. It is never stricter than the shared limit. It slows a flood from one address on the shared allowance and does not stop one.
338. **The setting `SLUICE_FACILITATOR_KILL_SWITCH` is documented as the switch to rely on** and the database key as the second, quicker one. The code already let either stop every send, and a test now holds the setting's with the stored switch turned off, deleted and unreachable.
339. **The guide's steps now use one database, and say that both services share one token**, what a bug or a compromise in the tool server could then do, and that separate databases are the stronger setup once there is a paid plan. The risks say the same. The way back to two databases is written down.
340. **The daily command estimate was counted on the stand-in and rests on stated assumptions**, shown both with a script as one command and with every command inside it counted, because Upstash's pages do not say which. A test adds it up.
341. **Upstash's per-user tokens limited to a key prefix are mentioned as untried**, not made a step: the documentation read did not say that the free plan has them or that they hold inside scripts.
342. **`.env.example` gained the one new name and no value.** An existing test of the serverless handlers now accepts the sharing, since it runs both services on one stand-in database.
343. **The test's limits on the length of the go-live mutation list moved from 60 to 120 to 139 to 180**, because the new entries brought it to 139. The lower limit is now the present number, so that dropping an entry fails the test, and the test also checks that no two entries share an id.
344. **The steps for moving to two databases say to move while nothing is calling the tools.** The tool server's record of what each payment was used for is not carried over: the facilitator refuses a payment it already holds, so nothing is served twice, and a caller whose answer was still pending cannot fetch it.
